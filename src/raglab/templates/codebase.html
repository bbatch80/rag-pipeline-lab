How the codebase is connected

One Python package, raglab, about 12,000 lines in 45 modules, with 58 test files beside it. Everything is reached through one command-line tool, raglab, and one web app. Think of it as three flows plus a governance layer.

Flow 1A document goes in

ingest.py is the front door. For each source file it computes a fingerprint (the bytes plus the processing recipe) and skips anything unchanged. New or changed files go through parsing/ (the PDF and markdown parsers, with parsecache.py remembering parses), then chunking.py (section-aware splitting with a size cap), then quality gates (a degenerate parse is quarantined, never indexed), then deid.py for PHI sources (pseudonymize before anything is stored), then indexcopy.py, which builds the search copy of each chunk: the text the ranker reads, with a context prefix and, for records, a header of the record's keys.

sources.py is the registry that says how each of the eleven sources behaves. embed.py turns chunks into vectors and raglab index builds the HNSW and BM25 indexes. The synth/ package generates the internal corpus and member records from the Synthea population; letters.py, opm.py, and roster.py fetch or load the real external sources.

Flow 2A question comes in

  1. Identity (identity.py, webapp.py): the session resolves to a document persona and a warehouse role. Identity is never a parameter a model can set.
  2. Context (retrieval.py, identifiers.py, recognizers.py): identifiers in the question or the surface (member, claim, case) are recognized by shape and check digit, looked up, and turned into filters. They are context, not search words.
  3. Route (router.py): code reads the question for plan years, plan codes, an as-of date, and scope, and applies the coverage rule (a program named without a plan means search every plan beneath it).
  4. Plan (planner.py, the biggest module): one call to a small model proposes the legs (document probes and named warehouse queries, at most three), and the code validates and repairs the plan with structural rules. Model plans, code governs.
  5. Search (retrieval.py): per-source hybrid search, vector plus BM25, fused by rank, under Postgres row-level security so an unauthorized chunk is never a candidate.
  6. Rerank (rerank.py): a cross-encoder scores every candidate against the question; the best score against a per-source threshold decides abstention.
  7. Warehouse (snowlane.py): named, parameterized Snowflake queries run as the caller's warehouse role; no freeform SQL.
  8. Payload (payload.py, context_services.py): one versioned JSON payload with status, chunks, provenance, and the plan, validated against the schema.
  9. Disclose (pipeline.py): the payload is written to the disclosure log before it's delivered; if the write fails, nothing is delivered.

webapp.py exposes this as JSON routes, ui.py and templates/ render it as the five surfaces, mcp_server.py exposes it as three MCP tools. All three call the same functions.

Flow 3Proving it works

eval_retrieval.py runs the golden set through the real pipeline per persona; checks.py scores each item by its declared shape (pages, values, rows, refusal); taxonomy.py groups items by the kind of work they ask for; the ratchet compares against eval/baseline.json.

benchmark.py measures index recall, recall-rls recall per persona, drift.py embedding drift, ablation.py the funnel with stages removed, rerankbakeoff.py and tablebakeoff.py the model and parser comparisons. dashboard.py renders the scorecard, console.py the health and audit views. smoke.py checks the live site after a deploy.

ThroughoutThe governance layer

It runs through all three flows: RLS policies and migrations in db/, deid.py with its owner-only vault, identity.py, and the disclosure log.
